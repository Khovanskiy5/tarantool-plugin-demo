# Сценарий демонстрации tarantool-idea-plugin

Проект подготовлен так, что каждая возможность плагина срабатывает
на готовых файлах. Порты кластера — **3311/3312/3315** (3301 занят
инстансом из `tarantool-learn`). Учётная запись — `client` / `secret`.

Что понадобится: IntelliJ IDEA 2026.1+ с установленным плагином;
для раздела «Данные» — Ultimate; для гуттер-иконок, автодополнения
и Emmy-отладки — плагин EmmyLua2.

## 1. Автоматика при открытии проекта

Откройте каталог `tarantool-plugin-demo` как проект. Сразу видно две
вещи:

* в IDEA Ultimate — уведомление о созданных **источниках данных**:
  плагин прочитал `config.yaml` и завёл `tarantool-plugin-demo-router-001-a@3315`
  и `tarantool-plugin-demo-storage-001-a@3311` (лидер). RO-реплика
  `storage-001-b@3312` сознательно пропущена;
* готовые конфигурации запуска в выпадающем списке Run — они лежат
  в `.run/` и подхватываются автоматически.

Ещё при открытии плагин молча разворачивает встроенные аннотации
EmmyLua в `.types/tarantool/bundled/` (каталог принадлежит плагину
и в git не хранится) — автодополнение по API работает сразу. Если
с окружением что-то не так (нет EmmyLua2, не найден tarantool,
устарели типы), появляется одна сводная нотификация с кнопками
починки — при исправном окружении её нет.

## 2. Схемы конфигурации YAML

Откройте `config.yaml`: в статус-баре — схема **Tarantool cluster
config** (официальная JSON Schema Tarantool 3). Нажмите Ctrl+Space
внутри секции `iproto:` или наберите новую опцию верхнего уровня —
автодополнение с документацией; опечатка в имени опции подсвечивается.
Схема активна потому, что рядом лежит `instances.yml` (второй триггер —
`tt.yaml` в корне).

Откройте `tt.yaml` — схема **tt environment config** (разделы `env`,
`app`, `modules`, `repo`, `ee`, `templates`).

## 3. Панель «Tarantool»

Внизу IDE — вкладка Tarantool: таблица трёх инстансов (`tt status`):
состояние, PID, режим RW/RO, готовность config и box; автообновление
каждые 5 секунд.

1. Нажмите **Запустить** — `tt start` поднимет кластер.
2. Убедитесь: `router-001-a` и `storage-001-a` в RW, `storage-001-b` в RO.
3. Кнопка **Логи** — хвост журнала (`tt log -f`) в Run-консоли. Строки
   вида `schema.lua:27 I> спейс users создан…` кликабельны — имя файла
   без каталога разрешается поиском по индексу проекта.
4. Кнопка **Консоль** — вкладка встроенного Терминала с `tt connect`
   к выбранному инстансу. Попробуйте:

   ```
   box.space.users:select()
   \set language sql
   SELECT * FROM SEQSCAN "users";
   ```

Кластер оставьте запущенным — он нужен для разделов 10–11 и 13.

## 4. Конфигурация «Tarantool» + LUA_PATH

Запустите **«Tarantool: hello.lua»**. Скрипт делает
`require('model.users')` — модуль лежит в `src/model/users.lua`
и находится потому, что флажок LUA_PATH добавил корень проекта и `src/`
в пути поиска. В выводе — кириллица, `_TARANTOOL`, аргументы
из конфигурации (`--from-run-config`).

Откройте Run → Edit Configurations → «Tarantool: hello.lua»: поля
скрипта/интерпретатора/аргументов/рабочего каталога, макросы
`$PROJECT_DIR$`, редактор переменных окружения, флажки LUA_PATH
и отладчика.

## 5. Кликабельные трейсбеки

Запустите **«Tarantool: кликабельный трейсбек»**. Скрипт падает; в
консоли ссылка `./src/model/users.lua:31` — клик открывает строку
с `error(...)`. Выше — строка журнала до падения: формат
`имя_файла:строка` тоже кликабелен.

## 6. Встроенный отладчик (tarantool -d)

Запустите **«Tarantool: встроенный отладчик (-d)»**. Скрипт стартует
под интерактивной консолью luadebug прямо в окне Run (флажок
конфигурации «Запустить со встроенным отладчиком»):

```
help            -- список команд
b debugger_demo.lua:12
c               -- continue до точки останова
p weight        -- печать переменной
n               -- шаг
c               -- до конца
```

Кнопка Debug у конфигураций «Tarantool» отключена сознательно — свой
протокол отладки плагин не реализует (для графической отладки — раздел 10).

## 7. Контекстный запуск и гуттер ▶

Правый клик по `scripts/hello.lua` в дереве проекта или редакторе →
**Run** — конфигурация создаётся автоматически. С установленным
EmmyLua2 в первой строке файла появляется гуттер-иконка ▶.
Файлы `*_test.lua` перехватывает раннер luatest (раздел 9), а не
обычный запуск — попробуйте правый клик по `test/users_test.lua`.

## 8. Конфигурация «tt (Tarantool CLI)»

В списке Run — папка tt: `tt start`, `tt stop -y`, `tt status`,
`tt log -f`, `tt check app.lua`. Любая команда tt выполняется в окне Run
с псевдотерминалом. В Edit Configurations поле «Команда» подсказывает
варианты, включая `log -f tarantool-plugin-demo:storage-001-a` —
имена инстансов берутся из `instances.yml`.

## 9. Раннер luatest

Запустите **«luatest: все тесты»** (или правый клик по
`test/users_test.lua` → Run). Дерево результатов строится из TAP-вывода:
группа `users`, 5 зелёных тестов. Сломайте любой assert — тест станет
красным с диагностикой.

Раннер запускает `.rocks/bin/luatest -o tap -v` — luatest уже
установлен в проект (`tt rocks install luatest`).

## 10. Графический отладчик: точки останова в любом файбере

Отладка живого инстанса — не «печать в лог», а обычная отладка: точка
останова, стек, значения переменных, шаги, условия, вычисление
выражений. Работает во всём коде, который исполняет Tarantool:
в фоновых файберах, в обработчиках iproto-запросов, внутри триггеров
спейса.

Почему это вообще возможно: в LuaJIT отладочный хук ставится на весь
VM, а не на отдельную корутину, поэтому он срабатывает в любом файбере
Tarantool — и в тех, что созданы до подключения IDE, и в тех, что
появятся потом. Останов не уступает файбер, а блокирует процесс в
C-коде, поэтому останавливаться безопасно даже внутри транзакции
и триггера.

Как это устроено: слушает не IDE, а сам процесс Tarantool — он открывает
порт отладчика (нативная библиотека emmy_core из плагина EmmyLua2),
а IDE подключается к нему.

### Запуск: одна кнопка (плагин 1.5.0+)

Выберите в панели Tarantool инстанс `storage-001-a` и нажмите
**«Запустить с отладчиком»** (иконка жучка). Плагин перезапустит именно
этот инстанс, подменив точку входа своим загрузчиком, дождётся открытия
порта и сам подключит сессию отладки. Ни строки в коде приложения, ни
переменных окружения, ни запуска из терминала.

Побочный эффект, ради которого всё и затевалось: загрузчик придерживает
запуск приложения до подключения IDE, поэтому **точки останова
срабатывают и в стартовом коде** — в `app.lua`, в `schema.bootstrap`,
в теле только что созданного файбера.

Скрипты отлаживаются так же просто: у конфигурации «Tarantool»
(например, «Tarantool: hello.lua») теперь работает кнопка **Debug**.

### Запуск: без плагина 1.5.0 (ручной сценарий)

Порт открывает само приложение — по секции `app.cfg` в `config.yaml`:

```yaml
app:
  file: 'src/app.lua'
  cfg:
    debugger:
      enabled: true
      instance: 'storage-001-a'
      port: 9966
```

Значения читает `src/debug_setup.lua`. Имя инстанса обязательно: все три
инстанса выполняют один `app.lua` и иначе боролись бы за один порт.
Дальше — **Запустить** в панели и **Debug** у конфигурации
«Tarantool: attach debugger» (её создаёт действие Tools → Настроить
Emmy-отладчик Tarantool). Проверка: в журнале `storage-001-a` строка
«отладчик слушает порт 9966». Вернуть обычный режим — `enabled: false`
и перезапуск.

В этом сценарии точки останова срабатывают только в коде, который
выполняется после подключения IDE: стартовый код к тому моменту уже
отработал.

Нагрузку для всех сценариев ниже даёт конфигурация **«Tarantool:
нагрузка для отладки»** (`scripts/debug_traffic.lua`): она стучится
в `storage-001-a` по iproto. Сценарий выбирается первым аргументом —
`big`, `checkout`, `queue`, `import` или `all` (по умолчанию `all 3`);
менять его удобно в Run → Edit Configurations → поле «Аргументы».

### 10.1. Точка останова в фоновом файбере

`src/model/queue.lua`, строка 29 (`local calculation =
orders.calculate(order)`) — тело обработчика очереди.

Запустите «Tarantool: нагрузка для отладки» с аргументом `queue 2`.

Что видно: выполнение встало в файбере **order-worker-1**; в Frames —
его собственный стек (`process` ← `pcall` ← `worker_loop`), в
Variables — `worker`, `job` с вложенным заказом и позициями. Повторный
Resume приводит ко второму останову — уже в **order-worker-2**:
точка ловит каждый файбер, а не «главный поток».

### 10.2. Точка останова в обработчике iproto-запроса

`src/api.lua`, строка 25 — тело `api.checkout`, вызываемое клиентом
через `conn:call`.

Запустите нагрузку с аргументом `checkout 2`.

Что видно: останов в файбере пула запросов (`pool#NN`, значение
переменной `handler`), стек `api.lua:25 ← [C]` — вызов пришёл из
iproto. В окне Run клиента напечатано «→ вызываю api.checkout…», а
ответа нет: клиент честно ждёт. Нажали Resume — в консоли клиента
появилась строка «✓ api.checkout за N с».

### 10.3. Точка останова внутри триггера спейса

`src/model/audit.lua`, строка 22 — триггер `on_replace` на спейсе
`orders`.

Любая запись в `orders` (та же нагрузка, или `box.space.orders:replace{…}`
в консоли) останавливает выполнение внутри чужой транзакции. В
Variables — `operation` (`INSERT`/`REPLACE`), `actor` с именем файбера,
`before` и `after` в виде обычных таблиц. Стек показывает, кто пишет:
`audit.lua ← [C] replace ← orders.lua:save ← api.lua:checkout`.

### 10.4. Условная точка останова и глубокий стек

`src/model/orders.lua`, строка 89 — тело рекурсивного `apply_rules`.
Правый клик по красному кружку → **Condition**: `current > 100000`.

Запустите нагрузку с аргументом `big`. Мелкие заказы проходят мимо,
останов происходит только на крупном. В Frames — четыре, пять и шесть
кадров подряд: рекурсия по дереву правил. Переключение между кадрами
показывает свои `depth`, `current`, `rule` в каждом — то, ради чего
стек и нужен.

### 10.5. Логпойнт: точка, которая не останавливает

`src/model/orders.lua`, строка 70. Правый клик по кружку → снимите
**Suspend**, включите **Evaluate and log** и впишите:

```
позиция {item.title} x{item.qty} = {line_total}
```

Теперь запуск нагрузки печатает поток строк в консоль отладчика, ничего
не останавливая, — отладочный `print` без правки кода и перезапуска
инстанса.

### 10.6. Несколько файберов на одной точке

`src/api.lua`, строка 95 — тело `api.import_batch`, которое выполняется
в файберах `import-1`, `import-2`, … Запустите нагрузку с аргументом
`import 3`: одна и та же строка останавливается по очереди в разных
файберах, и каждый раз стек и переменные — свои.

### 10.7. Вычисление выражений на остановленном инстансе

В окне Debug вкладка **Evaluate** (или список Watches) выполняет
произвольный Lua в контексте остановленного файбера:

```lua
require('fiber').self():name()
box.space.orders:count()
D(box.space.orders:get(order.id))
require('json').encode(calculation.trace)
api.stats()
```

Ограничение: выражение не должно уступать файбер (`fiber.sleep`,
сетевые вызовы) — процесс в этот момент стоит.

### 10.8. Tarantool-объекты в панели переменных

Тапл, `decimal`, `uuid`, `datetime`, `interval` — это cdata, и
отладчик EmmyLua показывает их пустым значением. Поэтому в проекте
есть `src/inspect.lua`: он ставит глобальную функцию `D()`, которая
разворачивает любое такое значение в обычную таблицу или строку.
В Watches:

```lua
D(tuple)                       --> { id = 900, total_amount = …, created_at = '…' }
D(box.space.orders:select({}, { limit = 3 }))
D(box.error.last())
```

В коде демо рядом с таплами намеренно лежат обычные таблицы
(`before`/`after` в `audit.lua`, `saved` в `api.lua`) — они видны
в Variables без всяких обходов.

### 10.9. Два бесконечных цикла: фоновый файбер и главный

Самый частый вопрос: «а если фоновый файбер с yield крутится вечно —
в него и в главный цикл воткнуться можно?» Проверяется за минуту
на `scripts/fiber_loops.lua` — там ровно это: фоновый файбер
`background-loop` и главный `main-loop`, оба с `fiber.yield()`.

1. Точки останова на строках 20 (`iteration = iteration + 1`)
   и 34 (`main_loop_iteration = main_loop_iteration + 1`).
2. Конфигурация **«Tarantool: два цикла с yield»** → кнопка **Debug**.

Останов приходит то в один цикл, то в другой: Resume в фоновом файбере
отдаёт управление главному, и наоборот. В Variables видно `iteration`
фонового и `main_loop_iteration` главного — каждый со своим значением,
растущим от останова к останову.

Во время любого останова работает **Evaluate** (⌥F8) и список Watches —
произвольный Lua в контексте остановленного файбера:

```lua
require('fiber').self():name() .. '#' .. require('fiber').self():id()
box.info.uptime
require('fiber').info()          -- все живые файберы процесса
D(box.space._space:select({}, { limit = 3 }))
```

Ограничение одно: выражение не должно уступать файбер (`fiber.sleep`,
сетевые вызовы) — процесс в этот момент стоит.

### Что стоит знать

* пока выполнение стоит на точке останова, стоит **весь инстанс**:
  Tarantool однопоточный. Клиенты ждут, репликация догоняет после
  Resume (проверено: `tt status` и `box.info.replication` возвращаются
  в норму сами);
* включённый отладчик выключает JIT: на этом проекте синтетический
  Lua-цикл замедляется примерно в 8 раз, смешанная нагрузка
  с обращениями к спейсам — примерно вдвое. Поэтому отладчик
  включается на одном инстансе и только на время разбора;
* при запуске кнопкой «Запустить с отладчиком» точки работают везде,
  включая стартовый код: приложение придерживается до подключения IDE.
  В ручном сценарии стартовый код (`schema.bootstrap`) успевает
  отработать до подключения — там точки в нём не сработают;
* обычный запуск инстанса не меняется: при `enabled: false` строки
  отладчика не делают ничего.

## 11. Данные через Database Tools (Ultimate)

Кластер должен работать (раздел 3). В окне **Database**:

* два источника, созданные автоматически, с драйвером
  **Tarantool (shim)** и SQL-диалектом Tarantool;
* откройте `tarantool-plugin-demo-storage-001-a@3311` → таблицы `users`,
  `orders` и `order_events` (видны потому, что у спейсов задан `format`;
  в `order_events` пишет триггер из раздела 10.3);
* двойной клик по `users` — грид с данными (кириллица, пагинация);
  `orders` открывается вместе с колонкой `created_at` типа `datetime` —
  ext-типы MsgPack (datetime, uuid, decimal, interval) декодирует
  форк `MsgPackLite` внутри shim-драйвера.
  Полный скан уже разрешён: в `config.yaml` включено
  `compat: sql_seq_scan_default: 'old'`;
* отредактируйте ячейку и нажмите Submit — запись проходит благодаря
  эмуляции автокоммита в драйвере-обёртке (каждая операция применяется
  сервером сразу; rollback честно предупреждает, что откат невозможен);
* откройте `playground/queries.sql` в SQL-консоли источника: `SEQSCAN`,
  `SET SESSION "sql_seq_scan"`, типы `UNSIGNED/STRING/UUID/DATETIME/MAP`,
  `LIMIT/OFFSET`, `AUTOINCREMENT` — ложных ошибок подсветки нет;
* в источнике роутера `@3315` таблиц нет — данные живут в хранилище.

Диалект назначается и вручную: Settings → Languages & Frameworks →
SQL Dialects → «Tarantool».

## 12. Генерация типов для EmmyLua2

Встроенные курированные аннотации (включая vshard) плагин развернул
сам при открытии проекта — `.types/tarantool/bundled/`. Действие
**Tools → Сгенерировать типы Tarantool** дополняет их интроспекцией
установленного Tarantool 3.8 в `.types/tarantool/generated/`.
Оба каталога принадлежат плагину и в git не хранятся; собственные
уточнения кладите в `.types/tarantool/manual/` — этот каталог плагин
не перезаписывает. Каталоги подключены через `.emmyrc.json`.
После индексации в любом `.lua`: `box.space.` → автодополнение,
`fiber.` → сигнатуры с документацией.

## 13. Просмотр .snap / .xlog

Кластер уже создавал снапшоты: откройте
`var/lib/storage-001-a/00000000000000000032.snap` двойным кликом —
YAML-расшифровка через `tt cat` в редакторе только для чтения
(видны INSERT спейса `users` с демо-данными). Рядом — `.xlog`.
Вывод длиннее 20 000 строк обрезается с пометкой.

## 14. Проверка синтаксиса (tt check)

Правый клик по любому `.lua` (редактор или дерево проекта) →
**Проверить синтаксис (tt check)** — уведомление «syntax is OK».
Внесите синтаксическую ошибку — уведомление покажет строку из stderr.

## 15. Live-шаблоны

Откройте `playground/live_templates.lua`, наберите `tspace` и Tab —
развернётся создание спейса с format и первичным индексом. Остальные:
`tonce`, `tfiber`, `tatomic`, `tnetbox`, `tlog`, `twatch`. Работают
в любом `.lua`-файле даже без EmmyLua2. Список: Settings → Editor →
Live Templates → Tarantool.

## 16. Мастер нового проекта

**File → New → Project… → Generators → Tarantool** — имя, каталог
и шаблон: `single_instance`, `cluster`, `vshard_cluster`,
`config_storage`. Плагин выполнит `tt init` и `tt create
--non-interactive` (для vshard — ещё `tt build`) и создаст `.gitignore`.
Демо-проект открыт отдельно, поэтому мастер удобно показать, создав
одноразовый проект, например, из шаблона `vshard_cluster`.

## 17. Режимы запуска: локально, Docker, Kubernetes

**Settings → Tools → Tarantool → Режим запуска** (хранится
в `.idea/tarantool.xml`):

* **Локально** — всё, что показано выше;
* **Docker** — префикс `docker compose exec tarantool`: панель, логи
  и консоль выполняют tt внутри контейнера. Заготовка —
  `docker-compose.yml` (проброшены порты 3311/3312/3315, том с проектом);
* **Kubernetes** — namespace + селектор подов: панель показывает поды
  (`kubectl get pods`), перезапуск — `kubectl delete pod` (пересоздаёт
  контроллер), логи — `kubectl logs -f`, консоль — `kubectl exec -it`.

Там же, в **Settings → Tools → Tarantool**, — пути к `tarantool` и `tt`,
если IDE не видит PATH шелла.
